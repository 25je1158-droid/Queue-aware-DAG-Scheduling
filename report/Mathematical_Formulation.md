# Mathematical Formulation

This document expresses the optimization problem described in the mid-evaluation report and maps it to the simulation's online heuristic. The formulation is an application-level completion-time minimization problem. The code implements an online heuristic for it; it does not solve the global optimization problem exactly.

## 1. Sets and parameters

- \(\mathcal{N}\): set of vehicles.
- \(\mathcal{M}\): set of MEC servers.
- \(G_n=(V_n,E_n)\): DAG application generated by vehicle \(n\).
- \(D_i\): input data size of task \(i\), in bits.
- \(C_i\): required CPU cycles of task \(i\).
- \(F_m\): maximum CPU capacity of MEC server \(m\), in cycles/second.
- \(R_m\): communication coverage radius of MEC server \(m\).
- \(B\): uplink bandwidth.
- \(d_{nm}(t)\): distance between vehicle \(n\) and server \(m\) at time \(t\).
- \(T^{contact}_{nm}(t)\): estimated remaining contact time.

## 2. Decision variables

- \(x_{im}(t)\in\{0,1\}\): 1 when task \(i\) is assigned to MEC server \(m\) at time \(t\).
- \(f_{im}(t)\geq 0\): CPU rate allocated to task \(i\) at server \(m\).
- \(S_i\): task execution start time.
- \(C_i^{finish}\): task completion time.
- \(T_{app}\): end-to-end completion time of the application.

## 3. Communication model

The simulation uses a simplified distance-dependent channel model:

\[
 g(d)=\frac{1}{1+(d/50)^2},\qquad
 SNR(d)=\frac{P_{tx}g(d)}{N_0}.
\]

The estimated uplink rate is:

\[
 R(d)=B\log_2(1+SNR(d)).
\]

Therefore, the estimated upload time for task \(i\) is:

\[
 T_i^{up}=\frac{D_i}{R(d_{nm}(t))}.
\]

This is a simplified simulation model, not a calibrated or measured radio channel.

## 4. Queue and computation model

Tasks first spend time uploading. After upload completion, they enter the selected MEC server's waiting queue. A task starts execution when a server execution slot becomes available. The simulation allows at most two concurrently running tasks per server.

For server \(m\), the online server-workload estimate used for candidate screening is:

\[
 \widehat T_{im}^{server}(t)=
 \frac{\sum_{j\in Running_m} C_j^{remaining}
       +\sum_{j\in Waiting_m} C_j^{remaining}+C_i}{F_m}.
\]

This work-conserving estimate is an approximation of queue-plus-service delay. It is not an exact queueing-theory formula.

During execution, CPU is shared among running tasks using critical-path weights. If \(w_i\) is the rank of running task \(i\), the allocation is:

\[
 f_{im}(t)=F_m\frac{w_i}{\sum_{j\in Running_m}w_j}.
\]

Thus, when a server has running tasks, the allocated shares sum to its CPU capacity:

\[
 \sum_{i\in Running_m}f_{im}(t)=F_m.
\]

The execution time of a task under a constant allocation is approximately:

\[
 T_i^{exe}=\frac{C_i}{f_{im}}.
\]

The full task delay can be written as:

\[
 T_i^{total}=T_i^{up}+W_{im}+T_i^{exe}+T_i^{result},
\]

where \(W_{im}\) is queue waiting time and \(T_i^{result}\) is result-transmission time. The current implementation treats result transmission as negligible and does not separately simulate it.

## 5. DAG precedence and critical-path rank

For every edge \((j,i)\in E_n\), task \(i\) can start only after task \(j\) completes:

\[
 S_i\geq C_j^{finish},\qquad \forall (j,i)\in E_n.
\]

If task \(i\) has multiple predecessors:

\[
 S_i\geq \max_{j\in Pred(i)}C_j^{finish}.
\]

The implementation calculates a task-specific critical-path rank using estimated execution time on the fastest MEC server:

\[
 Rank(i)=\frac{C_i}{F_{max}}+
 \max_{j\in Succ(i)}Rank(j),
\]

with \(Rank(i)=C_i/F_{max}\) for a terminal task. Ready tasks with higher rank are considered first. The same rank is used as the weight in CPU sharing.

## 6. Mobility and connectivity constraints

A server is a candidate only when the vehicle is within its coverage:

\[
 d_{nm}(t)\leq R_m.
\]

The trace contains vehicle position and scalar speed, but not heading. The simulation therefore estimates contact time as:

\[
 \widehat T^{contact}_{nm}(t)=
 \begin{cases}
 \infty,&v_n(t)\leq 0.1,\\
 \frac{R_m-d_{nm}(t)}{v_n(t)},&v_n(t)>0.1.
 \end{cases}
\]

This estimate assumes motion directly outward from the server and is a conservative approximation under that assumption. A candidate is rejected if:

\[
 T_i^{up}+\widehat T_{im}^{server}(t)
 >\widehat T^{contact}_{nm}(t).
\]

## 7. Resource and assignment constraints

Each task is assigned to at most one MEC server:

\[
 \sum_{m\in\mathcal M}x_{im}(t)\leq 1.
\]

The total allocated CPU at a server cannot exceed its capacity:

\[
 \sum_i x_{im}(t)f_{im}(t)\leq F_m,\qquad \forall m.
\]

CPU allocations are non-negative:

\[
 f_{im}(t)\geq 0.
\]

## 8. Deadline and application completion

Each task has a deadline relative to its application's release time. A completed task meets its deadline when:

\[
 C_i^{finish}\leq T_i^{deadline}.
\]

The application completes when all tasks have completed. Its completion time is:

\[
 T_{app}=\max_{i\in V_n}C_i^{finish}-T_n^{release}.
\]

## 9. Optimization objective

The target objective is:

\[
 \boxed{\min_{x,f,S}\;T_{app}}
\]

subject to DAG precedence, one-server assignment, MEC CPU capacity, non-negative CPU allocation, connectivity, mobility-feasibility and deadline constraints, together with dynamic queue evolution.

## 10. Online heuristic used in the code

At each simulation step, the implementation:

1. Replays the current vehicle position and speed from the SUMO trace.
2. Identifies tasks whose predecessors have all completed.
3. Sorts ready tasks by descending task-specific critical-path rank.
4. Evaluates reachable MEC servers and estimates upload plus queued/running workload delay.
5. Rejects candidates that fail the modeled contact-time feasibility check.
6. Selects the feasible server with the smallest estimated upload-plus-server-workload delay.
7. Places the task in the upload stage and then the server waiting queue.
8. Shares CPU among running tasks in proportion to their critical-path ranks.
9. Updates task, queue, server and application completion states.

This is a greedy online heuristic for the stated objective. It does not enumerate all possible global schedules or prove optimality.
