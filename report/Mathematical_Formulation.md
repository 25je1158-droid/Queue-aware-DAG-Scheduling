# Mathematical Formulation

This document formalizes the queue-aware DAG scheduling problem represented by
the simulator and distinguishes the mathematical target from the implemented
online heuristic. The code simulates the system in discrete time; it does not
solve the global optimization problem exactly or guarantee global optimality.

## 1. Sets, graph and parameters

- \(\mathcal{N}\): selected vehicles.
- \(\mathcal{M}\): MEC servers.
- \(G_n=(V_n,E_n)\): DAG application generated by vehicle \(n\).
- \(i\in V_n\): a task belonging to vehicle \(n\).
- \(D_i\): task input size in bits.
- \(C_i\): task CPU demand in cycles.
- \(F_m\): CPU capacity of MEC server \(m\), in cycles/second.
- \(R_m\): coverage radius of server \(m\).
- \(B\): uplink bandwidth.
- \(P_{\mathrm{tx}}\): transmit-power factor.
- \(N_0\): noise-power parameter.
- \(\Delta t\): simulation time step.
- \(K\): maximum number of concurrently running tasks per server.
- \(r_n(t)\): vehicle position at time \(t\).
- \(v_n(t)\): scalar vehicle speed at time \(t\).
- \(d_{nm}(t)\): distance between vehicle \(n\) and server \(m\).
- \(T^{\mathrm{rel}}_n\): application release time.

In the default simulation, \(\Delta t=0.1\) seconds, \(K=2\), the coverage
radius is \(300\) m, and the server capacities are \(8\), \(12\), and \(16\)
billion cycles/second. Each application has five tasks with edges
\[
E_n=\{(T1,T2),(T1,T3),(T2,T4),(T3,T4),(T4,T5)\}.
\]

## 2. Decision and state variables

- \(x_{im}\in\{0,1\}\): task \(i\) is assigned to server \(m\).
- \(f_{im}(t)\geq0\): CPU rate allocated to task \(i\) by server \(m\).
- \(T_i^{\mathrm{up}}\): upload duration.
- \(T_i^{\mathrm{ready}}\): time at which all DAG predecessors are complete.
- \(S_i\): execution start time.
- \(C_i^{\mathrm{finish}}\): execution completion time.
- \(W_i\): time spent waiting in the MEC queue.
- \(C_i^{\mathrm{rem}}(t)\): remaining CPU cycles.
- \(T_n^{\mathrm{app}}\): application completion time relative to release.

The implementation assigns a task once, when it is ready and a feasible server
is found. It then moves through the states
\[
\mathrm{new}\rightarrow\mathrm{uploading}\rightarrow
\mathrm{queued}\rightarrow\mathrm{running}\rightarrow\mathrm{done}.
\]

## 3. Distance and communication model

The distance used by the simulator is
\[
d_{nm}(t)=\sqrt{(x_n(t)-x_m)^2+(y_n(t)-y_m)^2}.
\]

The simplified path-loss gain and signal-to-noise ratio are
\[
g(d)=\frac{1}{1+(d/50)^2},\qquad
\mathrm{SNR}(d)=\frac{P_{\mathrm{tx}}g(d)}{N_0}.
\]

The estimated uplink rate is
\[
R(d)=B\log_2\left(1+\mathrm{SNR}(d)\right).
\]

For a task assigned at time \(t\), its upload duration is
\[
T_i^{\mathrm{up}}(t)
 =\frac{D_i}{\max(1,R(d_{nm}(t)))}.
\]

The `max(1, ...)` term is the implementation's numerical guard against
division by a rate below one bit/second. This is a simplified simulation
channel, not a calibrated wireless model. Result transmission is not modeled,
so \(T_i^{\mathrm{result}}=0\).

## 4. Queue and execution model

After uploading, task \(i\) enters the waiting queue of its assigned server.
At most \(K\) tasks can run simultaneously on server \(m\). Define
\[
\mathcal{R}_m(t)=\{\text{tasks running on }m\},\qquad
\mathcal{Q}_m(t)=\{\text{tasks waiting on }m\}.
\]

The candidate server's workload estimate in the implementation is
\[
\widehat{T}_{im}^{\mathrm{work}}(t)
=
\frac{
\displaystyle\sum_{j\in\mathcal{R}_m(t)}C_j^{\mathrm{rem}}(t)
+\displaystyle\sum_{j\in\mathcal{Q}_m(t)}C_j^{\mathrm{rem}}(t)
+C_i
}{\max(F_m,1)}.
\]

This estimate treats all remaining work as if it were served at the full
server capacity. It is therefore a workload score for comparing candidates,
not an exact prediction of queue delay when \(K\) tasks share CPU.

For each running task, let \(w_i>0\) be its critical-path rank. The simulator
allocates CPU at each time step according to
\[
f_{im}(t)=F_m
\frac{w_i}{\displaystyle\sum_{j\in\mathcal{R}_m(t)}w_j},
\qquad i\in\mathcal{R}_m(t).
\]

Consequently,
\[
\sum_{i\in\mathcal{R}_m(t)}f_{im}(t)=F_m
\quad\text{when }\mathcal{R}_m(t)\ne\varnothing.
\]

The discrete-time remaining-cycle update is
\[
C_i^{\mathrm{rem}}(t+\Delta t)
=\max\left(0,\,
C_i^{\mathrm{rem}}(t)-f_{im}(t)\Delta t\right).
\]

Task \(i\) completes during that step when
\[
C_i^{\mathrm{rem}}(t+\Delta t)=0,
\]
and the implementation records
\[
C_i^{\mathrm{finish}}=t+\Delta t.
\]

For a completed task, the measured queue wait is
\[
W_i=\max\left(0,\,
S_i-T_i^{\mathrm{ready}}-T_i^{\mathrm{up}}\right).
\]

Under a constant CPU allocation, the corresponding continuous-time
approximation is
\[
T_i^{\mathrm{exe}}\approx\frac{C_i}{f_{im}}.
\]
The simulator instead uses the discrete update above and permits the
allocation to change whenever the running-task set changes.

## 5. DAG precedence and critical-path priority

For every edge \((j,i)\in E_n\), task \(i\) is eligible only after task \(j\)
has completed:
\[
T_i^{\mathrm{ready}}\geq C_j^{\mathrm{finish}}.
\]

Equivalently, for multiple predecessors,
\[
T_i^{\mathrm{ready}}\geq
\max_{j\in\mathrm{Pred}(i)}C_j^{\mathrm{finish}}.
\]

The implementation uses a task-specific rank based on the fastest MEC server:
\[
\mathrm{Rank}(i)
=\frac{C_i}{F_{\max}}
+\max_{k\in\mathrm{Succ}(i)}\mathrm{Rank}(k),
\]
where the maximum over an empty successor set is zero. Thus, for a terminal
task,
\[
\mathrm{Rank}(i)=\frac{C_i}{F_{\max}}.
\]

Ready tasks are considered in descending rank order. The same rank is used as
the CPU-sharing weight \(w_i\).

## 6. Mobility and contact feasibility

A server can be considered only when the vehicle is within coverage:
\[
d_{nm}(t)\leq R_m.
\]

Because the trace contains speed but not heading, the simulator uses the
following conservative outward-motion approximation:
\[
\widehat{T}^{\mathrm{contact}}_{nm}(t)=
\begin{cases}
\infty, & v_n(t)\leq0.1,\\[4pt]
\displaystyle\frac{\max(0,R_m-d_{nm}(t))}{v_n(t)}, & v_n(t)>0.1.
\end{cases}
\]

For a candidate assignment, the implementation requires
\[
T_i^{\mathrm{up}}(t)
+\widehat{T}_{im}^{\mathrm{work}}(t)
\leq\widehat{T}^{\mathrm{contact}}_{nm}(t).
\]

Candidates failing this test are discarded. The contact estimate is a model
assumption and is not a trajectory-exact handover or connectivity model.

## 7. Assignment and resource constraints

Each task is assigned to at most one server:
\[
\sum_{m\in\mathcal{M}}x_{im}\leq1,
\qquad x_{im}\in\{0,1\}.
\]

An assigned task must use its selected server:
\[
f_{im}(t)=0\quad\text{when }x_{im}=0.
\]

The general MEC capacity constraint is
\[
\sum_{i\in V}f_{im}(t)\leq F_m,
\qquad \forall m\in\mathcal{M}.
\]

In the simulator, only running tasks receive positive allocations, and the
running-set size is bounded by
\[
|\mathcal{R}_m(t)|\leq K.
\]

## 8. Deadlines and application completion

Task \(i\) meets its deadline when
\[
C_i^{\mathrm{finish}}\leq T_i^{\mathrm{deadline}},
\]
where the default deadline is
\[
T_i^{\mathrm{deadline}}=T_n^{\mathrm{rel}}+20\ \text{seconds}.
\]

The application finishes only after every task in its DAG has finished:
\[
C_n^{\mathrm{app}}=
\max_{i\in V_n}C_i^{\mathrm{finish}}.
\]

The reported end-to-end application completion time is
\[
T_n^{\mathrm{app}}=
C_n^{\mathrm{app}}-T_n^{\mathrm{rel}}.
\]

## 9. Optimization objective

The intended application-level objective is
\[
\boxed{
\min_{\{x_{im}\},\{f_{im}(t)\},\{S_i\}}
\ \max_{n\in\mathcal{N}}
\left(C_n^{\mathrm{app}}-T_n^{\mathrm{rel}}\right)
}
\]
when minimizing the completion time of the slowest application.

For the reported experiments, the simulator does not solve this global
min-max problem. It reports the mean completion time of completed
applications,
\[
\overline{T}^{\mathrm{app}}
=\frac{1}{|\mathcal{N}_{\mathrm{completed}}|}
\sum_{n\in\mathcal{N}_{\mathrm{completed}}}
T_n^{\mathrm{app}},
\]
along with completion rates, queue wait, upload time, execution time, server
utilization and deadline violations. The queue-aware policy is therefore
evaluated using measured simulation outputs rather than an exact optimizer.

## 10. Online heuristic implemented in the code

At each simulation step, the implementation:

1. Replays vehicle position and speed from the SUMO trace.
2. Finds tasks whose predecessors are all in the `done` state.
3. Sorts ready tasks by descending \(\mathrm{Rank}(i)\).
4. For each task, evaluates servers satisfying coverage and contact feasibility.
5. Scores each feasible server by
   \[
   \mathrm{Score}_{im}(t)
   =T_i^{\mathrm{up}}(t)
   +\widehat{T}_{im}^{\mathrm{work}}(t).
   \]
6. Selects
   \[
   m_i^*(t)\in
   \arg\min_{m\in\mathcal{M}_{\mathrm{feasible}}}
   \mathrm{Score}_{im}(t).
   \]
7. Uploads the task and admits it to the selected server's waiting queue.
8. Starts queued tasks when execution slots are available.
9. Applies critical-path-weighted CPU sharing and updates remaining cycles.
10. Records task, application and server metrics until completion or the
    simulation time limit.

This is a greedy online heuristic. It does not enumerate global assignments,
future queue states, mobility trajectories or CPU schedules, and it provides no
proof of optimality.
